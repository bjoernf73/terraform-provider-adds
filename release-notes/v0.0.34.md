# v0.0.34

`adds_user` now fully owns the account's enabled state, and `adds_user_password` no longer
touches it. This removes the perpetual `enabled` drift that appeared when one resource
enabled an account the other wanted disabled.

## Fixed

- **`adds_user` now applies `sam_account_name` changes.** `user_update.ps1` reconciled the
  `name` (CN) and `userPrincipalName` but never the `sAMAccountName`, so renaming the logon
  name was silently skipped and read back as the old value — Terraform then reported
  "inconsistent result after apply". `sam_account_name` is now reconciled on both update and
  create-time adoption, matching `adds_group`, `adds_computer`, and `adds_gmsa` (which were
  unaffected). Case-only changes apply too.

- **`adds_user` no longer fights `adds_user_password` over `enabled`.** Previously a user
  created with `enabled = false` could be enabled as a side effect of `adds_user_password`,
  so every following plan showed `enabled = true -> false` and tried to re-disable the
  account. `adds_user` is now the single owner of the enabled state, and
  `adds_user_password` only sets the password, so there is no more back-and-forth.

- **`adds_user` enforces `enabled = true` on its own.** Enabling an account with no usable
  password used to be deferred to a password resource, so the account could stay disabled
  even though the plan said `enabled = true`. `adds_user` now sets a throwaway strong random
  password (25 characters, never written to state) purely so Active Directory allows the
  account to be enabled. The reset happens only when the account has no usable password, so
  a password already set by `adds_user_password` is never overwritten.

## Changed

- **`adds_user_password` no longer changes the account's enabled state.** The
  `enable_account` attribute has been removed; the resource sets the password and nothing
  else. Control the enabled state with `adds_user.enabled` instead. On upgrade, remove any
  `enable_account` argument from `adds_user_password` blocks and set `enabled = true` on the
  corresponding `adds_user` to keep the account enabled.

## Internal

- `SetUserPassword` dropped its `enable_account` parameter; `user_password_set.ps1` dropped
  the `Enable-ADAccount` call; `user_common.ps1` gained `New-EnableBootstrapPassword` and a
  reworked `Set-UserEnabledState`. `resource_user` Create/Update no longer override the
  read-back `enabled` value, since it is now authoritative. Tests, examples, and docs
  updated to match.
