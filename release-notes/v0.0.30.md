# v0.0.30

The provider no longer runs remote scripts through an in-memory, base64+gzip,
`Invoke-Expression` bootstrap. That technique is behaviourally identical to a PowerShell stager,
and behavioural antivirus (Microsoft Defender, `Behavior:Win32/PShellCobStager`) blocks it on
hardened hosts — the blocked process exited 0 with no output, which surfaced as the misleading
*"remote PowerShell returned no JSON output"* error on GPO operations. Each operation now stages
its script as a plain `.ps1` file and runs it with `-File`, which is indistinguishable from an
administrator running a script.

## Fixed

- **Remote scripts are staged and run as files, not decoded and executed in memory.** Every
  operation previously piped a gzip-compressed, base64-encoded script to a bootstrap that
  decompressed it and called `Invoke-Expression`. Defender's behavioural engine flags exactly
  that `FromBase64String` → `GZipStream` → `Invoke-Expression` sequence as a Cobalt Strike stager
  and terminates the process, leaving an empty stdout at exit code 0. Each operation now runs three
  small remote commands instead: a write bootstrap reads the script as **plain text** from stdin
  and writes it to `C:\Windows\Temp\adds-<token>.ps1`, the script is run with `pwsh -File <path>`,
  and the file is removed afterwards (best effort). None of the three performs any in-memory decode,
  decompression or `Invoke-Expression`, so they do not resemble a stager. The script body still
  travels on stdin rather than the command line, so the 8191 character `cmd.exe` limit is still
  respected, and no configuration, state or import IDs change.
- **A stray warning can no longer corrupt an operation's JSON.** stdout must contain nothing but
  the operation's JSON document, so the shared script prologue now silences the warning stream.
  This covers, for example, the `GroupPolicy` module's `WinPSCompatSession` notice, which could
  otherwise prepend text to stdout and break JSON decoding.

## Internal

- `internal/powershell` replaces `BuildCommand`/`EncodeScript` (the stdin IEX bootstrap and its
  gzip+base64 encoder) with `NewScriptToken`, `RemoteScriptPath`, and `BuildWriteCommand` /
  `BuildFileCommand` / `BuildDeleteCommand`. The staged path is never quoted on the command line:
  `cmd.exe` strips the outer quote pair when a line carries four or more quotes, which would mangle
  the executable, so the only quotes on the line are the ones around the PowerShell path, and the
  token-based temp path never contains spaces.
- `client.runPowerShellOnce` now orchestrates write → run → delete, decoding CLIXML on each result
  and surfacing the run step's exit code and stderr as before. The empty-stdin sentinel and all the
  v0.0.28/v0.0.29 transport and client retries are unchanged and still apply to the write step.
- Embedded scripts are required to stay ASCII so the plaintext stdin transfer is encoding-safe
  regardless of the remote console code page; staged files are written as UTF-8 with a BOM so both
  Windows PowerShell 5.1 and PowerShell 7 read them back correctly under `-File`.
- The obsolete, log-only `stdin_winrm_repro_test.go` investigation harness was removed; it probed
  the deleted bootstrap and its questions are resolved.
