# v0.0.31

`adds_json_gpo_export` no longer hangs while exporting comments or script files under
Windows PowerShell. Exports also preserve the correct computer/user enabled settings
when `gpo_powershell_path` is set to `pwsh`. Both fixes were verified against a live GPO
under both PowerShell editions; the default remains `powershell.exe`.

## Fixed

- **`adds_json_gpo_export`: JSON serialization could hang under Windows PowerShell.**
  Strings returned by `Get-Content` carry filesystem and provider metadata. Windows
  PowerShell 5.1 traverses that metadata during deep JSON serialization, which could
  stall `terraform plan` or surface a WinRM internal error. Comment and script-file
  lines are now converted to plain strings before serialization, preserving their text
  without exporting PowerShell metadata.
- **`adds_json_gpo_export`: computer/user settings could be incorrectly exported as
  disabled under `pwsh`.** The Windows PowerShell compatibility layer loses nested
  `Get-GPO` properties such as `.Computer.Enabled`. The export now derives both enabled
  settings from the GPO's AD `flags` attribute instead, so native and compatibility
  exports agree. Previously exported JSON may contain incorrect enabled settings;
  re-export it before using it with `adds_json_gpo`.
- **Remote execution errors now include the selected PowerShell executable and any
  captured stderr.** Transport errors retain their underlying cause, making failures
  under `powershell_path` or `gpo_powershell_path` easier to diagnose.

## Internal

- Added local export regression tests for comment/script serialization and all four
  AD enabled-flag combinations under Windows PowerShell and PowerShell 7. These tests
  use stub AD cmdlets and do not require a domain controller.
- Added an opt-in, read-only live export comparison, gated by `ADDS_HOST` and
  `ADDS_GPO_EXPORT_NAME`, with diagnostic phase markers and enabled-setting parity checks.
- Added client tests covering execution-error context and script cleanup after a failure.
